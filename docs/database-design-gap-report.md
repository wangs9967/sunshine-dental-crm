## 数据模型差异

- 16 表基线现统一为 18 表，加入 `product_stock_records` 和 `redemption_credentials`。项目前期提及的库存流水原稿在可见工作区和 Git 历史中未找到，本表是基于已确认流程形成的第二阶段定义。
- 月限额字段统一为 `per_user_monthly_limit`，订单只允许 `pending`、`verified`。订单显式记录 `created_at TIMESTAMPTZ`，复用同一个时点确定月份和写入订单。
- 两类流水均通过普通 `exchange_order_id` 外键关联订单，受追加保护，每个订单最多各关联一条扣减。事务服务校验会员、商品、金额和数量并同步更新快照。此次精简将 `CHECK` 从 48 项减至 18 项，`UNIQUE` 从 21 项减至 19 项。常规枚举、时间组合、分类条件及摘要格式移到 FastAPI 服务，保留金额和数量有效性、流水算术、订单状态与核销完整性等数据库约束。
- 订单、积分及库存流水的幂等列统一为 `VARCHAR(128) NOT NULL`。API 明确请求头格式、唯一范围、重放和冲突响应；两类流水由服务端生成各自的幂等键。见 [API 幂等键契约](api-spec.md#幂等键契约)。
- 移除订单内静态核销码，改用短时凭证、订单行锁和同事务消费及审计。同一订单最多一条未关闭凭证、最多一条已消费凭证。固定角色权限以四角色矩阵提供，系统配置只开放明确批准的键。
- 三端契约保留扫码引导注册、普通跟进和家访、后台生成复查名单与员工手动联系。员工代录、普通员工核销和店长敏感写权限按待确认事项控制。

## 月限兑索引评审

采用 B-tree **`(member_id, product_id, created_at) INCLUDE (quantity, status)`**。会员和商品是等值前缀，创建时间是范围列，三者均进入索引条件。保留原 `(member_id, created_at DESC)` 用于会员订单列表，保留 `(status, created_at DESC)` 用于后台状态队列。日期转换在查询前计算并绑定 UTC 参数，查询直接比较时间列。单列 `created_at` 只能收窄时间段，仍需筛掉其他会员和商品。

在 PostgreSQL 16.16 的隔离回滚事务中，用 80,003 条合成订单对同一查询执行 `EXPLAIN (ANALYZE, BUFFERS)`。所有测试行和对象均已回滚。

| 索引方案 | 实际查询计划 |
|---|---|
| 新复合索引可用 | 使用 `ix_orders_member_product_created`，索引扫描返回 13 个候选项，两轮验证中查询节点命中 14–15 个共享缓冲块 |
| 移除复合索引，增加日期单列索引并保留旧列表索引 | 规划器选用旧 `ix_orders_member_created`，索引扫描返回 103 个候选项，其中 90 行被商品条件过滤，命中 103 个共享缓冲块 |

两次执行返回相同聚合结果。样本用于验证列顺序和访问路径，生产规模下的索引选择仍由数据分布和统计信息决定。

## 验证和后续准入

- 精简版 DDL 已在 PostgreSQL 隔离事务验证。核对 18 张表、自然月边界、原复合索引计划、负余额与负库存、非法订单数量及月限额、订单幂等唯一键、流水只追加、无效订单外键、重复扣减和一次性核销。测试对象与数据已回滚。
- Mermaid 解析及结构交叉核对通过，API、权限矩阵和页面使用同一组 18 个权限编号。现有后端 pytest 两项通过，健康检查测试仍有 Starlette TestClient 弃用提示。
- FastAPI 服务校验、角色授权、交易并发、页面交互和视觉用例待实现后执行。本轮只在 PostgreSQL 回滚事务中验证 DDL，未创建或运行 Alembic 迁移，未开发业务接口或三端 UI。
- 最终设计评审关注四类运营决策：手机号和员工开通，积分与库存策略，动态凭证参数与角色授权，以及可访问的 Figma 基线。完整列表见[待确认事项](open-questions.md)。评审通过后再生成首个 Alembic 迁移，并按本契约启动三端 UI。
