# V1.0 兑换详细设计

## 已确认配置

`BUSINESS_TIMEZONE` 是服务端业务配置，默认且已确认值为 `Asia/Shanghai`（UTC+8）。自然月边界统一通过 IANA 时区计算，独立于服务器系统时区、数据库会话时区和会员手机时区。客户端无需传入时区或订单创建时间。

## 订单时间和查询边界

1. 兑换事务先锁定会员积分账户，检查订单幂等键。命中同一请求时返回原订单，并保留原 `created_at`。新订单再锁定商品。
2. 新订单在取得锁后取一次服务端当前时间作为本次拟写入的 `created_at`。以该时间确定额度查询窗口，建单时显式写入同一个值，字段类型为 `TIMESTAMPTZ`。即使提交时跨月，成功订单仍计入 `created_at` 所属月。
3. 将该时间换算为 `Asia/Shanghai` 的本地时间。取该自然月首日 `00:00:00` 和下月首日 `00:00:00`，将两个带时区的边界分别转换成 UTC，得到 `month_start_utc` 和 `next_month_start_utc`。跨年时以日历计算下月首日。
4. 按以下条件查询。限额有值时，校验已用数量加本次数量不超过 `per_user_monthly_limit`。`NULL` 跳过额度检查，仍校验库存和积分。额度检查、扣减和建单在同一事务中完成。

```sql
SELECT COALESCE(SUM(quantity), 0)
FROM exchange_orders
WHERE member_id = :member_id
  AND product_id = :product_id
  AND status IN ('pending', 'verified')
  AND created_at >= :month_start_utc
  AND created_at < :next_month_start_utc;
```

边界参数绑定为带时区的 UTC 时间。使用 B-tree `ix_orders_member_product_created (member_id, product_id, created_at) INCLUDE (quantity, status)`，两个等值条件位于时间范围条件之前。`quantity` 和 `status` 作为覆盖列。规划器是否选择仅索引扫描取决于页面可见性和成本。订单成功提交才占用额度，事务回滚不会留下占额记录。核销仅更新状态与核销信息，`created_at` 保持固定。

## 兑换事务与流水

1. PostgreSQL `READ COMMITTED` 下先锁积分账户，再锁商品，事务内以锁后的独立查询读取最新已提交额度。校验商品状态、数量、价格、库存、积分和限额。库存调整与商品写操作遵循相同商品锁约定。
2. 使用订单 UUID 创建记录。`product_snapshot` 包含名称、封面对象键、分类和单件积分价格，积分价格按十进制字符串表示。`quantity` 是正整数，服务端检查乘积在 BIGINT 范围内且账户余额充足。
3. 同一事务写入订单、积分账户快照、积分扣减流水、库存快照、库存扣减流水。积分与库存扣减分别等于订单成本和数量的相反数，失败全部回滚。商品快照或兑换结果不含动态核销凭证。
4. 三处数据库键均使用 `VARCHAR(128) NOT NULL`。订单按 `(member_id, idempotency_key)` 唯一，持账户锁查询原始请求头所对应的订单。两类兑换扣减流水各自使用 `exchange:<order_id>`，请求摘要沿用对应订单。人工调整用 `points-adjust:<digest>` 或 `stock-adjust:<digest>`，`digest` 为对 `[认证账号 UUID, 原始请求头]` 的规范 JSON 计算的 SHA-256 小写十六进制。调整流水在各自表中按键唯一。操作账号、请求头和操作命名空间决定复用范围。同一范围的键改用于另一个会员或商品时返回冲突。
5. 应用对已校验的请求字段计算 SHA-256，将 32 字节摘要保存在 `request_fingerprint`。摘要字段见 [API 契约](api-spec.md#幂等键契约)，使用无多余空格的 UTF-8 JSON 数组，UUID 使用规范小写形式，积分和数量先规范化为整数，原因使用校验后的文本。数据库唯一键处理并发重复提交；若发生同一幂等唯一键冲突，先回滚失败事务，再读取既有记录，按摘要决定重放或冲突。锁、扣减及业务写入在同一数据库事务中。

FastAPI 服务校验流水分类与来源、订单和流水的会员或商品是否一致、变动方向、操作人及调整原因。兑换积分变动必须等于订单成本的相反数，库存变动必须等于订单数量的相反数。数据库保留快照非负、流水算术与只追加约束，并通过普通订单外键及唯一订单引用防止重复扣减流水。

## 动态核销

签发与刷新由订单会员发起。服务端锁住待核销订单，作废上一条未关闭凭证并生成新的随机凭证，存储 SHA-256 摘要、签发和过期时间。原始值只通过不缓存的签发响应返回。更新失败时原凭证状态随事务回滚。有效期与刷新策略见待确认事项。

核销主体由服务端按角色授权。通过凭证摘要找到候选订单，按与签发相同的顺序先锁订单，再重新读取并校验凭证。有效区间为 `[issued_at, expires_at)`。服务端用同一个时点记录凭证消费与订单核销，连同脱敏审计在同一事务提交。并发请求中只允许一次成功，稍后请求收到已核销或凭证错误。已核销订单在任何月份都保留原 `created_at` 和额度占用。

## 边界示例

2026 年 11 月的业务查询区间是 `[2026-10-31T16:00:00Z, 2026-11-30T16:00:00Z)`。北京时间 `2026-11-30 23:59:59.999999` 属于 11 月，`2026-12-01 00:00:00` 属于 12 月。见[验收用例](test-cases.md#自然月限兑边界和跨月兑换)。
